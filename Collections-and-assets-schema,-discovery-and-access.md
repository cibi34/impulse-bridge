# Collections and assets schema, discovery and access

Version 3.11, 28/11/2025

## Definitions

### Id schema

    lowercase-chars-numbers-and-hyphens

Necessary (even if not obvious why): Uniformity, no special characters disallowed (colons, etc.) or with potential semantics in the storage context (spaces and dots in filesystems, etc.), etc.

Usually autogenerated by a name or title: Uppercase characters converted to lowercase, spaces and other allowed symbols converted to hyphens, multiple subsequent hyphens converted to single.

### Resource schema

    id-schema.extension

Extension shall specify content-type so content-type/extension association shall be fully defined elsewhere and adopted platform-wide (the reason behind that is that some asset-processing dependencies (sadly) rely on extension to determine content-type). If content-type metadata are also available, they shall be consistent with the extension (perhaps even auto-generated at the backend) and supplied only for searching and similar purposes.

### API response schema

    {
        "code": <integer code, 0 is success, other values interpreted per platform spec>,
        "message": "<message string, human-readable, user-oriented (not too much info)>",
        "data": [
            <data entries>
        ]
    }

Data entries are structured according to the the semantics of the returned results and per the serving backend's documentation.

## Searching

All endpoints that return lengthy result sets support searching. All search pattern values shall be URL-encoded.

Basic searching in all supported fields at once:

    s=<search pattern>

Search patterns can include the * wildcard.

Advanced searching per service-specific logic:

    s=<service-specific search pattern>

Refer to endpoint documentation (i.e., collection and asset services documentation) for the syntax and semantics of service-specific search patterns.

## Pagination

All endpoints that return lengthy result sets support pagination. Pagination is possible by means of specifying result set offset and count:

    o=<offset>&c=<count>

Offset and count parameters are positive integers. If offset is not specified then results start at the beginning of the result set. If count is not specified then all results up to the end of the result set are returned. In other words, default values for offset and count are 0 and (l - 1), respectively, where l is the length of the entire result set. In case of illegal values the entire result set shall be returned.

## Collections

A set of digital assets. A location is uniquely identified by an id and pointed-to by a URI. Assets in a collection can either be identified by an asset id resolved against the collection’s URI, in which case the URI also serves to point to a specific location on the Internet where assets are available, or by an absolute URI. In all cases, a collection’s URI serves as a point-of-access to asset discovery facilities.

## Assets

Digital assets comprising a collection. An asset is uniquely identified by either a literal following resource-schema which is resolved against the collection’s URI, or an absolute URI. This facilitates definition of collections that contain assets either accessible under a common location (e.g., files on a filesystem, blobs in a database, etc.) or each referenced individually and directly (e.g., in case of collections consisting of assets at different locations, each potentially shared among multiple collections).

### Asset metadata

#### Internally used metadata for discovery, access, management and rendering

Mandatory:

| Item | Definition | Remarks |
| :---- | :---- | :---- |
| assetID | Unique ID for the asset within the owner collection. | This is not always available and not always straightforward to derive, especially in cases of aggregate collections containing external assets referenced by absolute assetURIs. No other item among those adopted can be used (the “identifier” is not relevant here as it is more of a DOI referencing the original asset at its authoritative location, may indeed be unique but too cumbersome to use as ID, just like the assetURI.) Needs to be auto-generated or manually specified during mass asset import or individual asset management via the web frontend and admin tools. For consistency, it shall follow id-schema (which can additionally help with auto-generation). |
| assetURI | Absolute or relative URI to actual asset. |  |
| contentType | Mime-type of the asset with additional internals. |  |
| previewURI | Absolute or relative URI to asset preview. |  |
| published | Flag indicating whether the asset is published for client use or not, true/false. | Administrators can toggle this for collection management purposes, allows “removing” an asset from a collection without actually deleting it and in an easily reversible fashion, similar functionality to hiding/unhiding. |
| scale | | |

Note that, as discussed above, if **assetURI** or **previewURI** are relative or, more specifically, literals following resource-schema, then they are resolved against the collection’s URI, in which case they end up as **\<collection URI\>/\<asset URI\>** and **\<collection URI\>/\<preview URI\>**.

### Asset discovery

For each collection, the **GET \<collection URI\>/assets** endpoint provides information on all assets in the collection in the form of an array of entries each containing asset metadata as above. (It follows that “assets” is a platform-reserved symbol; you cannot have an asset named “assets” as it would conflict with the endpoint.)

Data returned by the **GET \<collection URI\>/assets** endpoint:

    [
        {
            "assetID": "ancient-temple",
            "title": "Ancient Temple",
            "description": "Part of an ancient temple.",
            "contentType": "model/gltf-binary",
            "scale": "1",
            "assetURI": "ancienttemple.glb",
            "previewURI": "ancienttemple.JPG"
            "contributor": "unknown",
            "description": "An ancient temple.",
            "identifier": "0001",
            "rights": "unknown"
        },
        {
            "assetID": "bad-taste",
            "title": "Bad Taste",
            "description": "Bad Taste.",
            "contentType": "model/gltf-binary",
            "scale": "1",
            "assetURI": "http://multiverse.dcarts.uoa.gr:65302/impulse/platform/collections/leuven-extras/BadTaste.glb",
            "previewURI": "http://multiverse.dcarts.uoa.gr:65302/impulse/platform/collections/leuven-extras/BadTaste.JPG",
            "contributor": "unknown",
            "description": "Some bad taste.",
            "identifier": "0002",
            "rights": "unknown"
        }
    ]

Notice that for the first asset a relative resource-schema literal is returned, therefore the asset is identified by resolving the literal against the collection’s URI, while for the second an absolute URI is specified, therefore that asset is accessed directly.

The results may not include all information available for every asset returned as the backend may not support that when assets are retrieved en masse. In that case, the asset information endpoint shall be used on individual assets to retrieve all information available for each one of them at a later stage. Asset ids shall always be returned. Ideally, titles shall also be returned to facilitate presentation of results by the requesting client.

(As an implementation recommendation for clients performing asset discovery via asset service nodes interfacing with curator or aggregator APIs that do not provide a direct asset preview URL for assets retrieved en masse in a single operation, the client should present results in the form of a textual list without preview thumbnails or using a standard thumbnail per asset type. The client should, of course, never try to retrieve the missing asset preview URLs by repeatedly invoking the asset information endpoint on each and every asset returned by asset discovery as this is bad form and will most certainly result in blocking.)

Note that the endpoint may return either a API-response-schema or a JSON array, depending on whether it is served by a backend, a plain file, a database, etc. This needs to be handled client-side. In both cases, the data returned are indeed valid JSON by specification \[TODO: ref\]. This approach enables deployment of collection asset discovery services on a per-collection basis, based on simple HTTP-accessible JSON files (i.e., an **assets** file under the collection’s URI), backend-served endpoints, database resources, etc.
